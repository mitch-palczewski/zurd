## Project

**zurd** — a multiplayer immersive 3D game by the Feed Collective. Players steer a
trans-dimensional trophy room through space, deploy objects to build islands of matter,
and defend against roving *Zurd* skulls that eat objects and, if left unchecked, the ship.

## Stack & versions

- **Godot Engine 4.7.2-stable — .NET (mono) edition** (see `project.godot` → `config/features = ("4.7", "Forward Plus")`).
- **GDScript** for all gameplay code. **C#** is used only for the lidar hardware input (`scripts/lidar/`, `scenes/tools/lidar_setup/`), because the RPLidar driver is a .NET library (`RpLidar.NET`, vendored and patched under `thirdparty/RpLidar.NET/`). The project is configured for .NET (`[dotnet] project/assembly_name="zurd"`).
- The mono editor expects the **.NET 10 SDK** (runtime `10.0.12`, from SDK `10.0.x`; `winget install Microsoft.DotNet.SDK.10 --source winget`). It is now required to build the C# lidar code; without it the GDScript game still runs but the lidar scripts won't compile.
- Renderer: **Forward+**. Stretch `canvas_items` / `expand` (explicit viewport size was removed from `project.godot`).
- Physics: **Jolt Physics** (`project.godot` → `[physics] 3d/physics_engine="Jolt Physics"`), chosen to reduce object edge-snagging.
- Input actions are ship-centric: `ship_pitch_up/down` (W/S), `ship_yaw_left/right` (A/D), `ship_boost` (Shift), `ship_launch` (Space). The old `move_*` WASD actions were removed.

## How to run

There is **no CLI build or test loop**. The only NuGet package is `System.IO.Ports` (serial ports, used by the lidar driver); Godot restores it the first time it builds the C# project (needs internet once). After pulling C# changes, press **Build** (hammer icon, top right of the editor) before running.
"Running on localhost" means running the game from the Godot editor:

1. Open the project in the **Godot 4.7.2 .NET (mono) editor** (*Import* → select this folder).
2. Press **F5** (play main scene) or **F6** (play current scene).
3. Main scene is `res://scenes/ui/loading_screen/boot.tscn` → main menu → world.

Headless import check (only if a Godot binary is on PATH): `godot --headless --path . --quit`.

## Entry flow & key systems

- **Entry:** `boot.tscn`/`boot.gd` → `SceneChanger.change_scene(...)` → main menu → `SceneChanger.change_scene_async(...)` → `toroidal_world.tscn` (extends `base_world.tscn`).
- **Autoloads (globals, registered in `project.godot`):** `EventBus` (`scripts/autoload/event_bus.gd`, signals `spawn_requested(Node3D)`, `object_eaten(actor, obj, mass)`, swat/pointer input, and the sculpture-mass events `object_hit`, `object_fused`, `masses_merged`, `objects_broken_off`, `cloud_progress_changed`, `cloud_formed`), `SceneChanger` (`scripts/autoload/scene_changer.gd`, threaded async loading), `ObjectTracker` (`scripts/autoload/object_tracker.gd`, tracks every Zurd target: loose launched `RigidBody3D`s and fused `MassPiece`s; `register_object`/`unregister_object`, `object_registered` signal, `is_trackable`, `get_random_object`, `get_closest_object`).
- **Spawn flow:** anything emits `EventBus.spawn_requested(node)`; `BaseWorld._on_spawn_requested` adds it under `ObjectContainer`. Launched projectiles also self-register with `ObjectTracker`.
- **Player** (`scenes/characters/player/`): `PlayerShip` (`CharacterBody3D`) coordinates `PlayerFlightController` (flight physics, emits `impact_occured`) and `LaunchObjectComponent` (spawns/launches random projectiles from `projectile_scenes`, gravity-free with linear-damp braking, spin, spread, and a player collision exception until the object clears).
- **Enemy** (`scenes/characters/enemy/`): `Zurd` (`CharacterBody3D`) is a thin coordinator over three components — `ZurdTargetComponent` (picks a target from `ObjectTracker`, CLOSEST/RANDOM), `ZurdMovementComponent` (steering + raycast obstacle avoidance against layer 1; holds the mouth on the target while eating; pushes masses it bumps), `ZurdMouthComponent` (eats the target, a loose object or a fused `MassPiece`, after it stays in the mouth for `eat_duration`; interrupted if it leaves or on swat; emits `object_eaten`).
- **GLB physics importer** (`scripts/import/glb_post_importer.gd`, `@tool EditorScenePostImport`): importing a `.glb` auto-generates two scenes under `scenes/objects/` — a `static/` `StaticBody3D` (convex-hull colliders + the `golf_terrain` material) and a `rigid/` `RigidBody3D` (AABB box collider + vertex colors). Meshes are shared `.res` files under `assets/meshes/`; vertex-color materials go to `assets/materials/objects/`.
- **Toroidal world** (`scenes/world/toroidal_world.gd` + `scripts/utils/toroidal_utils.gd`): wraps RigidBody3D/CharacterBody3D positions at world bounds.
- **Sculpture masses** (`scenes/sculpture/`; spec and plan in `claude/plans/`): `MassManager` (node in `base_world.tscn`, holds all tunables) watches every body registered with `ObjectTracker`, counts hits, and does fusing, merging, eating and breaking off. Contact callbacks only queue requests; the queue runs in the manager's `_physics_process`, because shapes can't change inside a physics callback. Each mass is one `SculptureMass` (`RigidBody3D`): fused objects become `MassPiece` nodes holding their visuals, while their `CollisionShape3D`s move onto the mass (meta `mass_piece` points back). Leaving a mass spawns a fresh instance of the object's scene. The blend look is `assets/shaders/sculpture_mass.gdshader` (one material per mass; the 100% cloud look is a placeholder). `SculptureFx` hooks placeholder effects to the EventBus signals. Test scene: `sandbox/test_sculpture_mass.tscn` (threshold 5, `hits_to_fuse` 1, debug labels).

## Conventions Claude must follow

- **Commit messages** (from README): `tag(scope): description`. Tags: `feat`, `fix`, `docs`, `asset`, `tool`, `refactor`. Example: `feat(player): Added flight controls`.
- **GDScript style:** indent with **tabs** (matches the majority of files); keep typed vars/returns and `class_name` as existing scripts do; use `push_warning`/`push_error` for diagnostics, not `print`.
- **C# style (lidar code only):** standard .NET — 4-space indent, file-scoped `namespace Zurd.Lidar;`, nullable enabled. A Godot node's class must be `partial` and its name must match its file name (`LidarSetup.cs` → `class LidarSetup`), so these files are PascalCase unlike the snake_case `.gd` files. Keep device logic in plain classes under `scripts/lidar/`; scenes only display it.
- **Vendored code (`thirdparty/`):** keep upstream's style so it can be compared with upstream. Mark every change with a `// zurd patch:` comment and list it in that folder's README.
- **Collision layers:** 1 Environment · 2 Player · 3 Objects · 4 Enemies · 5 UI.
- **Globals available everywhere:** `EventBus`, `SceneChanger`, `ObjectTracker`.
- **Do not hand-edit generated files** — `scenes/objects/{static,rigid}/*`, `*.import`, `*.uid` (including `*.cs.uid`) come from the importer/engine; re-import the source `.glb` instead.
- **Do not** edit `.godot/` (gitignored) or commit `.vscode/`.

## Known gaps (documented, not yet fixed)

- `scenes/ui/loading_screen/boot.gd` default `initial_scene_path` points at `.../menus/main_menu/main_menu.tscn` but the file is at `.../menus/main_menu.tscn` (extra folder). Relies on an Inspector override — likely a bug.
- `scripts/autoload/scene_changer.gd` calls a global `LoadingScreen`, but `LoadingScreen` is **not** registered under `[autoload]` in `project.godot`.
- Indentation is inconsistent: `glb_physics_importer.gd` uses spaces; most `.gd` files use tabs. `.editorconfig` sets charset only, not indent style.
