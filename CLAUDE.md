# CLAUDE.md

Guidance for Claude Code when working in this repository. For a fuller tech-stack
walkthrough see [claude/ONBOARDING.md](claude/ONBOARDING.md); for game concept, commit
standards, collision layers and autoloads see [README.md](README.md).

## Project

**zurd** — a multiplayer immersive 3D game by the Feed Collective. Players steer a
trans-dimensional trophy room through space, deploy objects to build islands of matter,
and defend against roving *Zurd* skulls that eat objects and, if left unchecked, the ship.

## Stack & versions

- **Godot Engine 4.7.2-stable — .NET (mono) edition** (see `project.godot` → `config/features = ("4.7", "Forward Plus")`).
- **GDScript** for all gameplay code. **C#** is used only for the lidar hardware input (`scripts/lidar/`, `scenes/tools/lidar_setup/`), because the RPLidar driver is a .NET library (`RpLidar.NET`, vendored and patched under `thirdparty/RpLidar.NET/`). The project is configured for .NET (`[dotnet] project/assembly_name="zurd"`).
- The mono editor expects the **.NET 10 SDK** (runtime `10.0.12`, from SDK `10.0.x`; `winget install Microsoft.DotNet.SDK.10 --source winget`). It is now required to build the C# lidar code; without it the GDScript game still runs but the lidar scripts won't compile.
- Renderer: **Forward+**. Stretch `canvas_items` / `expand` (explicit viewport size was removed from `project.godot`).
- Physics: **Jolt Physics** (`project.godot` → `[physics] 3d/physics_engine="Jolt Physics"`), chosen to reduce object edge-snagging.
- Input actions are ship-centric (Ship-Controls Design Doc §6.1). Keyboard: `ship_forward/reverse` (W/S), `ship_turn_left/right` (A/D), `ship_rise/sink` (Shift/Ctrl), `ship_launch` (Space, pilot launch), `launch_station_prev/fire/next` (J/K/L), `ship_swat` (left click). **Controllers are bound per device through profiles** (Ship-Controls Design Doc §6.3), never in Project Settings: the `Controllers` autoload gives each connected controller a `ControllerProfile` and binds it to that device only, so the 8BitDo and the arcade kit work at once. *Standard gamepad* is the 8BitDo layout (left stick or d-pad, Y/A or the triggers, B, LB/X/RB for the launch station) and the default; *Arcade kit* is empty until learned on the Controller Setup screen. The main menu's *Controllers* section picks a profile (or Off) per controller. Choices and learned layouts are saved per computer in `user://controller_config.json`; controller events found in Project Settings are dropped at startup with a warning. The main menu's controls label is built from the live input map (keyboard and mouse), so it always shows the current keys. Code reads input actions only, never keys or devices. The old pitch/yaw/boost and `move_*` actions were removed. There is one control scheme, *Stick drives* (joystick forward moves the ship forward); the *Stick lifts* alternative and its main-menu selector were removed.

## How to run

There is **no CLI build or test loop**. The only NuGet package is `System.IO.Ports` (serial ports, used by the lidar driver); Godot restores it the first time it builds the C# project (needs internet once). After pulling C# changes, press **Build** (hammer icon, top right of the editor) before running.
"Running on localhost" means running the game from the Godot editor:

1. Open the project in the **Godot 4.7.2 .NET (mono) editor** (*Import* → select this folder).
2. Press **F5** (play main scene) or **F6** (play current scene).
3. Main scene is `res://scenes/ui/loading_screen/boot.tscn` → main menu → world.

Headless import check (only if a Godot binary is on PATH): `godot --headless --path . --quit`.

## Entry flow & key systems

- **Entry:** `boot.tscn`/`boot.gd` → `SceneChanger.change_scene(...)` → main menu → `SceneChanger.change_scene_async(...)` → `zurd_world.tscn` (extends `base_world.tscn`). If an async load fails, `SceneChanger.load_failed` fires: the loading screen closes and the menu re-enables its buttons.
- **Autoloads (globals, registered in `project.godot`):** `EventBus` (`scripts/autoload/event_bus.gd`, signals `spawn_requested(Node3D)`, `object_eaten(actor, obj, mass)`, swat/pointer input, the sculpture-mass events `object_hit`, `object_fused`, `objects_combined`, `object_resized`, `masses_merged`, `objects_broken_off`, `cloud_progress_changed`, `cloud_formed` plus the `eat_requested` request, and the ship-control events `launch_selection_changed`, `station_activity_changed`), `SceneChanger` (`scripts/autoload/scene_changer.gd`, threaded async loading), `ObjectTracker` (`scripts/autoload/object_tracker.gd`, tracks every Zurd target: loose launched `RigidBody3D`s and fused `MassPiece`s; `register_object`/`unregister_object`, `object_registered` signal, `is_trackable`, `get_random_object`, `get_closest_object`), `Controllers` (`scripts/autoload/controllers.gd`, controller profiles per device: `get_devices`, `set_profile`, `save_learned_profile`, `reset_profile`, `devices_changed` signal; `connect_device(device, name, guid)` also lets tests fake a controller).
- **Spawn flow:** anything emits `EventBus.spawn_requested(node)`; `BaseWorld._on_spawn_requested` adds it under `ObjectContainer`. Launched projectiles also self-register with `ObjectTracker`.
- **Player** (`scenes/characters/player/`; design in `claude/design/`, plan in `claude/plans/archive/`): `PlayerShip` (`CharacterBody3D`) coordinates `PlayerFlightController` ("fish in water" flight: thrust, turn, rise and sink with eased inputs; coasts to a hover with a gentle drift and cockpit bob; turns only around global Y so the projected view never pitches or rolls; ground clearance, lowest altitude and ceiling; emits `impact_occurred`). `LaunchObjectComponent` (`LaunchMuzzle`) is the one shared launcher: `launch_object(scene, side_offset)` (random from its catalog when null) launches straight ahead from the middle of the ship, or moved sideways to a station's own side. The **object catalog** (`ObjectCatalog`, `data/object_catalog.tres`; hardening plan step 4) lists the launchable objects: one entry per object, a scene plus one group from the catalog's `groups` (labels only for now; `Unsorted` is always offered). Random launches pick evenly over entries with a scene; stations step through them in list order (`get_object_count`, `get_object_scene`). Every launched object carries its group as meta `catalog_group` (`ObjectCatalog.group_of(node)`); a `MassPiece` takes it over while fused and hands it back on break-off. Its *Sync with rigid scenes* tool button appends every scene in `scenes/objects/rigid/` that isn't listed (group `Unsorted`), saves, and reports empty entries, duplicates, unknown groups and scenes that break the collider contract (below). A catalog that lists a missing scene fails to load (and the ship with it), so remove an object's entry before deleting its scene. Launches are gravity-free with linear-damp braking, spin, spread, part of the ship's velocity, and a player collision exception until the object clears. Under `Stations`, each `LaunchStation` is one launch button with its own cooldown and side offset, and each `StationActivity` reports a station going active or empty (`station_activity_changed`). A station with previous/next actions keeps a selected object (Launch-Station Design Doc): the first press shows it on its `LaunchPreview` (`Cockpit/Interior/StationPreview`, a pedestal with a turning, mesh-only copy of the object), later presses step, and Launch fires it until the preview hides `preview_hide_delay` (5 s) after the last press. Then the station launches random objects again; `launch_selection_changed` fires with the scene, or null on hide.
- **Enemy** (`scenes/characters/enemy/`; **temporary**: a Zurd design doc and a full overhaul are coming, so don't build on these scripts; `ZurdSpawner` is deliberately not in any world while the sculpture system is tested, so there is one hand-placed Zurd): `Zurd` (`CharacterBody3D`) is a thin coordinator over three components — `ZurdTargetComponent` (picks a target from `ObjectTracker`, CLOSEST/RANDOM), `ZurdMovementComponent` (steering + raycast obstacle avoidance against layer 1; holds the mouth on the target while eating; pushes masses it bumps), `ZurdMouthComponent` (eats the target, a loose object or a fused `MassPiece`, after it stays in the mouth for `eat_duration`; interrupted if it leaves or on swat; fires its own `bite_taken` and hands the bite to the `MassManager` with `EventBus.eat_requested`, which takes one part of a combined object or the whole object and emits `object_eaten`).
- **GLB physics importer** (`scripts/import/glb_post_importer.gd`, `@tool EditorScenePostImport`; the project's default for scene imports via `[importer_defaults]` in `project.godot`, so new models need no import setup; a launchable one then needs a catalog entry, via *Sync with rigid scenes* on `data/object_catalog.tres`). It only touches models under `assets/models/`, and the folder opts each model into scenes: `objects/` → a `rigid/` `RigidBody3D` scene under `scenes/objects/` (one convex-hull collider, the exact hull of the mesh, at scale 1 and centred where the model's middle is + vertex colors), `scenery/` → a `static/` `StaticBody3D` scene (convex-hull colliders + vertex colors), any other folder (e.g. `characters/`) → no scenes. Every model gets its meshes as shared `.res` files under `assets/meshes/` and its vertex-color materials under `assets/materials/objects/`; a model left directly in `assets/models/` gets those plus a warning. Old copies of `Arch_01`, `Archway` and `Crocodile_01` still sit directly in `assets/models/` next to their current copies in `objects/`, and both copies write the same mesh and material files; `Zurd_01` still sits there too instead of `characters/` (see Known gaps). The launcher and the sculpture-mass code depend on that collider layout (the catalog's check enforces it): `ObjectParts` reads an object's size from its first collision shape's scale and the launcher overwrites that scale, `MassPiece.get_center` averages shape positions, and growth break-off and the spin estimate measure each box or convex hull by its bounding box (`MassPiece.get_shape_bounds`); other shape types are left out of those measurements. Exact hulls cost more physics time than the old boxes (about 2.4× for 150 loose objects pressed together, 1.3× with fusing on; measured 2026-11-10). Changing the importer doesn't reimport existing models: select them in the FileSystem dock and press *Reimport* in the Import dock.
- **World** (`scenes/world/`): `zurd_world.tscn` is the playable world: `base_world.tscn` plus `terrain.tscn` (`Terrain`, a `@tool` procedural landscape built in `_ready`, with a trimesh collider on layer 1 and a water plane at sea level). The world does **not** wrap (decided 2026-11-04; the toroidal world and `ToroidalUtils` were removed). Teleportation may come later for a small part of the map.
- **Sculpture masses** (`scenes/sculpture/`; spec in `claude/design/`, plan in `claude/plans/archive/`): `MassManager` (node in `base_world.tscn`, holds all tunables) watches every body registered with `ObjectTracker`, counts hits, and does fusing, combining, merging, eating and breaking off. Contact callbacks only queue requests; the queue runs in the manager's `_physics_process`, because shapes can't change inside a physics callback. Each mass is one `SculptureMass` (`RigidBody3D`): fused objects become `MassPiece` nodes holding their visuals, while their `CollisionShape3D`s move onto the mass (meta `mass_piece` points back). Leaving a mass spawns a fresh instance of the object's scene. Matching objects (same model) that reach the hit count **combine** into one bigger object instead of fusing (Design Doc §4.10): every object carries an `ObjectParts` record (`scenes/sculpture/object_parts.gd`; meta `object_parts` on loose bodies, `MassPiece.parts` when fused) with each part's size and the size after each join; `combine_size_mode` adds volumes or scales. Counts, weights and cloud progress use parts, a growing piece knocks off the fused neighbours it now overlaps, and Zurds bite one part at a time (last added first). Before 100% fused objects use `assets/shaders/sculpture_mass.gdshader` (one material per mass; opaque so they stay solid and cast shadows, shifting only part of the way toward white). At 100% the mass swaps to its own copy of `sculpture_cloud.gdshader` with a white `burst` that settles over `cloud_transition_time`, `SculptureFx` puffs every object up (around its middle) and leaves it 1.2× bigger, and the cloud holds `cloud_rise_delay` before rising, so becoming a cloud is a jump, not a fade. The cloud look itself is a placeholder. `SculptureFx` hooks placeholder effects to the EventBus signals. Test scene: `sandbox/test_sculpture_mass.tscn` (threshold 5, `hits_to_fuse` 1, debug labels).

## Workflow: plan before code, questions on review

- **No major code changes without a reviewed plan.** Before modifying any code, scene, shader or
  project setting, write a plan document in `claude/plans/` named `YYYY-MM-DD-<topic>-plan.md`
  (goal, files to touch, steps, risks, how it will be verified, open questions). Then stop and
  ask the user to review it. Start implementing only after the user explicitly approves the
  plan, and keep the changes inside the approved scope. If the work needs to grow beyond the
  plan, update the plan and get it approved again first.
  - Exempt: edits to docs/plans themselves, and trivial fixes the user asks for directly
    (typos, a one-line change they spelled out). When unsure, write the plan.
- **Reviewing design docs and plans** (`claude/design/`, `claude/plans/`): when asked to review,
  or when writing a new one, ask as many clarifying questions as needed to fill gaps,
  ambiguities, contradictions with other docs or the code, missing edge cases and unstated
  tunables. Put them in **one numbered list** so the user can answer by number (`3: yes`), and
  group them under short headings if there are many. Don't fill gaps with silent assumptions:
  ask, or list the assumption as a question. After the answers come back, update the doc and
  ask follow-up questions (numbering continues) until nothing is open.

## Conventions Claude must follow

- **Commit messages** (from README): `tag(scope): description`. Tags: `feat`, `fix`, `docs`, `asset`, `tool`, `refactor`. Example: `feat(player): Added flight controls`.
- **File and folder names:** snake_case (the Godot standard; it avoids case problems in exported builds), except C# files, which must match their class.
- **GDScript and shader style:** indent with **tabs** (the GDScript style guide; every `.gd` and `.gdshader` file uses them and `.editorconfig` sets it); keep typed vars/returns and `class_name` as existing scripts do; use `push_warning`/`push_error` for diagnostics, not `print`.
- **C# style (lidar code only):** standard .NET — 4-space indent, file-scoped `namespace Zurd.Lidar;`, nullable enabled. A Godot node's class must be `partial` and its name must match its file name (`LidarSetup.cs` → `class LidarSetup`), so these files are PascalCase unlike the snake_case `.gd` files. Keep device logic in plain classes under `scripts/lidar/`; scenes only display it.
- **Vendored code (`thirdparty/`):** keep upstream's style so it can be compared with upstream. Mark every change with a `// zurd patch:` comment and list it in that folder's README.
- **Collision layers:** 1 Environment · 2 Player · 3 Objects · 4 Enemies · 5 UI (named in Project Settings → Layer Names, so the Inspector shows them).
- **Globals available everywhere:** `EventBus`, `SceneChanger`, `ObjectTracker`, `Controllers`.
- **Do not hand-edit generated files** — `scenes/objects/{static,rigid}/*`, `assets/meshes/*`, `assets/materials/objects/*`, `*.import`, `*.uid` (including `*.cs.uid`) come from the importer/engine; re-import the source `.glb` instead.
- **Do not** edit `.godot/` (gitignored) or commit `.vscode/`.

## Known gaps (documented, not yet fixed)

- **Lidar touches don't reach gameplay yet.** Only `MouseSwatInput` emits `EventBus.swat_requested` / `pointer_moved`. The bridge (`LidarManager`, step 4 of the lidar plan) waits until a lidar is set up against a screen or projection.
- **Zurds are temporary** (see Enemy above). Known issues for the overhaul: swatting has no minimum scale, so a Zurd can shrink to zero; scale tweens aren't stopped before a new one starts.
- **Model files aren't snake_case** (`Arch_01.glb`), and the importer copies those names into every generated scene, mesh and material. Rename them in the editor, renaming their generated files too (steps in `assets/models/README.md`). Before that: delete the old root copies `assets/models/{Arch_01,Archway,Crocodile_01}.glb` (the current ones are in `objects/`) and move `Zurd_01.glb` into `characters/`, both in the FileSystem dock.
- **Nothing despawns:** loose objects float forever and clouds never leave. There is no object budget or session reset yet.
- **No committed tests.** Verification so far used scratch headless harnesses that weren't kept.
