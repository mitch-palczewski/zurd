# CLAUDE.md

Guidance for Claude Code when working in this repository. For a fuller tech-stack
walkthrough see [claude/ONBOARDING.md](claude/ONBOARDING.md); for game concept, commit
standards, collision layers and autoloads see [README.md](README.md).

## Project

**zurd** — a multiplayer immersive 3D game by the Feed Collective. Players steer a
trans-dimensional trophy room through space, deploy objects to build islands of matter,
and defend against roving *Zurd* skulls that eat objects and, if left unchecked, the ship.

## Stack & versions

- **Godot Engine 4.7.2-stable — .NET (mono) edition** (see `project.godot` → `config/features = ("4.7", "Forward Plus")`).
- **GDScript** for all gameplay code. **C#** is used only for the lidar hardware input (`scripts/lidar/`, `scenes/tools/lidar_setup/`), because the RPLidar driver is a .NET library (`RpLidar.NET`, vendored and patched under `thirdparty/RpLidar.NET/`). The project is configured for .NET (`[dotnet] project/assembly_name="zurd"`).
- The mono editor expects the **.NET 10 SDK** (runtime `10.0.12`, from SDK `10.0.x`; `winget install Microsoft.DotNet.SDK.10 --source winget`). It is now required to build the C# lidar code; without it the GDScript game still runs but the lidar scripts won't compile.
- Renderer: **Forward+**. Stretch `canvas_items` / `expand` (explicit viewport size was removed from `project.godot`).
- Physics: **Jolt Physics** (`project.godot` → `[physics] 3d/physics_engine="Jolt Physics"`), chosen to reduce object edge-snagging.
- Input actions are ship-centric (Ship-Controls Design Doc §6.1). Keyboard: `ship_forward/reverse` (W/S), `ship_turn_left/right` (A/D), `ship_rise/sink` (Shift/Ctrl), `ship_launch` (Space, pilot launch), `launch_station_prev/fire/next` (J/K/L), `ship_swat` (left click). **Controllers are bound per device through profiles** (Ship-Controls Design Doc §6.3), never in Project Settings: the `Controllers` autoload gives each connected controller a `ControllerProfile` and binds it to that device only, so the 8BitDo and the arcade kit work at once. *Standard gamepad* is the 8BitDo layout (left stick or d-pad, Y/A or the triggers, B, LB/X/RB for the launch station) and the default; *Arcade kit* is empty until learned on the Controller Setup screen. The main menu's *Controllers* section picks a profile (or Off) per controller. Choices and learned layouts are saved per computer in `user://controller_config.json`; controller events found in Project Settings are dropped at startup with a warning. The main menu's controls label is built from the live input map (keyboard and mouse), so it always shows the current keys. Code reads input actions only, never keys or devices. The old pitch/yaw/boost and `move_*` actions were removed. There is one control scheme, *Stick drives* (joystick forward moves the ship forward); the *Stick lifts* alternative and its main-menu selector were removed.

## How to run

There is no CLI build for the game itself. The only NuGet package is `System.IO.Ports` (serial ports, used by the lidar driver); Godot restores it the first time it builds the C# project (needs internet once). After pulling C# changes, press **Build** (hammer icon, top right of the editor) before running.
"Running on localhost" means running the game from the Godot editor:

1. Open the project in the **Godot 4.7.2 .NET (mono) editor** (*Import* → select this folder).
2. Press **F5** (play main scene) or **F6** (play current scene).
3. Main scene is `res://scenes/ui/loading_screen/boot.tscn` → main menu → world.

**Tests** (`tests/`, see `tests/README.md`): one command runs them all headless in game mode (safe while the editor is open) in about half a minute, with the Godot 4.7.2 .NET *console* exe (not on PATH; it sits next to the editor exe):
`<Godot console exe> --headless --fixed-fps 60 --path . -s res://tests/run_tests.gd > "$TEMP/zurd_tests.txt" 2>&1` — exit code 0 and `RESULT: PASS` when everything passed. Add `-- unit` or `-- test_<name>` to run some only. The tests never touch `user://`, and the run fails if a guarded file changed.

Headless import check (only if a Godot binary is on PATH): `godot --headless --path . --quit`.

## Entry flow & key systems

- **Entry:** `boot.tscn`/`boot.gd` → `SceneChanger.change_scene(...)` → main menu → `SceneChanger.change_scene_async(...)` → a world (`zurd_world01.tscn`, the menu's main entry, or `zurd_world02.tscn`, the iteration in progress; both extend `base_world.tscn`). If an async load fails, `SceneChanger.load_failed` fires: the loading screen closes and the menu re-enables its buttons.
- **Autoloads (globals, registered in `project.godot`):** `EventBus` (`scripts/autoload/event_bus.gd`, signals `spawn_requested(Node3D)`, `object_eaten(actor, obj, mass)`, swat/pointer input, the sculpture-mass events `object_hit`, `object_fused`, `objects_combined`, `object_resized`, `masses_merged`, `objects_broken_off`, `cloud_progress_changed`, `cloud_formed` plus the `eat_requested` request, the ship-control events `launch_selection_changed`, `station_activity_changed`, and the Zurd events `object_launched`, `zurd_anger_changed`, `zurd_state_changed`, `zurd_stunned`, `zurd_driven_off`), `SceneChanger` (`scripts/autoload/scene_changer.gd`, threaded async loading), `ObjectTracker` (`scripts/autoload/object_tracker.gd`, tracks every Zurd target: loose launched `RigidBody3D`s and fused `MassPiece`s; `register_object`/`unregister_object`, `object_registered` signal, `is_trackable`, `get_random_object`, `get_closest_object`), `Controllers` (`scripts/autoload/controllers.gd`, controller profiles per device: `get_devices`, `set_profile`, `save_learned_profile`, `reset_profile`, `devices_changed` signal; `connect_device(device, name, guid)` also lets tests fake a controller, and `config_path` / `set_config_path(path)` let tests use their own config file).
- **Spawn flow:** anything emits `EventBus.spawn_requested(node)`; `BaseWorld` adds it to its container under `Actors` (`get_container_for`): `SculptureMass` → `Masses`, `Zurd` → `Zurds`, `SwatProjectile` → `Projectiles`, anything else (launched objects, objects broken off a mass) → `Objects`. Launched projectiles also self-register with `ObjectTracker`.
- **Player** (`scenes/characters/player/`; design in `claude/design/`, plan in `claude/plans/archive/`): `PlayerShip` (`CharacterBody3D`) coordinates `PlayerFlightController` ("fish in water" flight: thrust, turn, rise and sink with eased inputs; coasts to a hover with a gentle drift and cockpit bob; turns only around global Y so the projected view never pitches or rolls; ground clearance, lowest altitude and ceiling; emits `impact_occurred`). `LaunchObjectComponent` (`LaunchMuzzle`) is the one shared launcher: `launch_object(scene, side_offset)` (random from its catalog when null) launches straight ahead from the middle of the ship, or moved sideways to a station's own side. The **object catalog** (`ObjectCatalog`, `data/object_catalog.tres`; hardening plan step 4) lists the launchable objects: one entry per object, a scene plus one group from the catalog's `groups` (labels only for now; `Unsorted` is always offered). Random launches pick evenly over entries with a scene; stations step through them in list order (`get_object_count`, `get_object_scene`). Every launched object carries its group as meta `catalog_group` (`ObjectCatalog.group_of(node)`); a `MassPiece` takes it over while fused and hands it back on break-off. Its *Sync with rigid scenes* tool button appends every scene in `scenes/objects/rigid/` that isn't listed (group `Unsorted`), saves, and reports empty entries, duplicates, unknown groups and scenes that break the collider contract (below). A catalog that lists a missing scene fails to load (and the ship with it), so remove an object's entry before deleting its scene. Launches are gravity-free with linear-damp braking, spin, spread, part of the ship's velocity, and a player collision exception until the object clears. Under `Stations`, each `LaunchStation` is one launch button with its own cooldown and side offset, and each `StationActivity` reports a station going active or empty (`station_activity_changed`). A station with previous/next actions keeps a selected object (Launch-Station Design Doc): the first press shows it on its `LaunchPreview` (`Cockpit/Interior/StationPreview`, a pedestal with a turning, mesh-only copy of the object), later presses step, and Launch fires it until the preview hides `preview_hide_delay` (5 s) after the last press. Then the station launches random objects again; `launch_selection_changed` fires with the scene, or null on hide.
- **Enemy** (`scenes/characters/enemy/`; design: `claude/design/Zurd Core Design Doc.md` §12 for iteration 2, built in playtested iterations by `claude/plans/2026-11-11-zurd-overhaul-plan.md`, `claude/plans/2026-11-17-zurd-personality-plan.md` and `claude/plans/2026-11-20-zurd-growth-and-packs-plan.md`; the fuller Zurd AI Design Spec is the idea bank): a cast of roles, each Zurd with its own anger and temperament. **Roles** are `ZurdRole` resources in `data/zurd_roles/` (`shadow.tres`, `grazer.tres`, `sentinel.tres`): a home (`Home.SHIP` / `PACK` / `WATCH`), sight radius, anger amounts and tolerance, travel speed, a Shadow's distance and view arc, a placeholder tint, and the temperament ranges. **`ZurdTemperament`** (temper, patience, greed, boldness, curiosity, pace, body: its starting size) is rolled per Zurd from its role. **`ZurdAnger`** is now per Zurd (a plain class, unit-tested): it rises when the Zurd notices mess past `tolerated_in_view` (only the items beyond it), sees the ship launch while it does (every launch it sees holds the anger), its watched sculpture grows past `tolerated_sculpture_size`, or it's swatted or rammed, each times its temper; it falls after `calm_delay`, times its patience, and by `fed_calm` per part of a thrown object it eats; the Zurd turns Hostile at `hostile_threshold` and calms below `calm_threshold` after `hostile_cooldown`. **`ZurdDirector`** (in `game_systems.tscn`) spawns the cast when the world starts (`spawn_at_start`; tests turn it off): `grazer_count` Grazers in `pack_count` fixed packs (inner class `GrazerPack`; `add_pack` / `join_pack` for tests) whose middles start spread by a sunflower spiral (`spread_over_disc`) over `grazing_radius` around `grazing_center` and then roam it at `pack_speed`: each heads for the nearest loose object within `pack_scent` that no other pack is nearer to (rising or sinking to it), else a spot within its scent at its own height, keeps about `pack_spacing` from the other packs and stays on the disc; members wander `pack_radius` around the middle, `sentinel_count` Sentinels at the hand-placed landmarks (`Marker3D`s in group `zurd_landmarks`, one Sentinel each; extras hang out near the nearest), `shadow_count` Shadows at spots around the ship (`get_shadow_bearings`: within the role's view arc, a quarter step off dead ahead). It keeps one Zurd per target (`claim` / `release` / `is_claimed_by_other`, per piece for sculptures), tells Zurds that see the ship launch, tells a Sentinel when its sculpture grows, and every half second (`update_sentinels`) sends the nearest free Sentinel to each sculpture left unchanged for `settle_time`, spawning extra Sentinels up to `sentinel_cap` (an extra becomes a Grazer in the smallest pack when its sculpture goes; others go back to a landmark). When a cloud forms, every Zurd that can see it gives chase (`start_cloud_chase`, sized by `CloudSky.get_cloud_radius`). It adds the testing HUD (`scenes/ui/hud/zurd_testing_hud.tscn`: the 5 Zurds nearest the ship with role, state and anger, their average as nearby anger, role counts, settled sculptures); with `show_testing_hud` on, each Zurd also shows an anger bar (a `Label3D` made in code: green to yellow to red at the hostile threshold, arrows while rising or falling, same size on screen, hidden past 800 m). **`Zurd`** (`CharacterBody3D`, group `zurds`; `setup(role, rng)` before it spawns, `set_role` to switch) is Passive (decides per object whether to eat the loose objects it sees with `get_appetite()`: its greed when calm, rising to 1 with its anger, re-decided after `appetite_recheck`; goes after those at `feeding_speed`, eats each bite in `passive_eat_time`; with nothing to eat it keeps to its home: a Shadow wanders around `get_ship_spot()` carrying the ship's velocity, heading back at the role's `travel_speed`, and swoops back at `swoop_speed` once it has been out of the camera's view for `view_lost_time` (`is_swooping`); a Grazer wanders around its pack's middle; a Sentinel circles `get_watch_center()`, only Sentinels watch) or Hostile (red overlay; hunts by role via `ZurdSightComponent`, a sight cylinder over `ObjectTracker`: a Shadow the loose object in sight nearest the ship, then the largest sculpture over the limit; a Grazer loose objects within `hunt_radius` of its pack's middle (`find_area_target`), then any sculpture there, then strays in sight; a Sentinel its sculpture; only what it sees, no world-wide fallback; bites take the mouth's `eat_duration`). A Hostile Zurd calming down with a target finishes it first (`is_calming`). `take_swat` (swat projectiles, and the ship ramming via `PlayerShip`): a timid Zurd (boldness under `timid_below`) is driven off by one swat; a bolder one takes `bold_swats` (2–4 by boldness, plus one per `growth_per_swat` it has grown), each before the last stunning it and adding attack anger; driven off, it retreats `retreat_distance` from the ship, stays `away_time`, and comes back calm with its count reset; a `hit_cooldown` makes one swat volley or ram count once; a launched object entering its `HitArea` at `object_hit_speed` is food (`catch_object`): it stops in the air, the Zurd claims it and eats it at `catch_eat_speed`, each part calming it by `fed_calm`; no stun, not a swat. A `Label3D` health bar shows the swats. **Growth:** every part a Zurd eats adds `growth_per_bite` to its `size` (starting at its temperament's `body`, up to `max_size`, kept for good); `set_size` scales its mesh, body, mouth and hit-area shapes (its own copies; the scene shares them), labels and kept distances, and its speeds by size^−`size_slowdown`; the body node stays unscaled. **Cloud chase:** a chasing Zurd (`is_chasing_cloud`) drops its target and hostility (anger down to the calm threshold), flies at the cloud at `chase_speed`, bounces off it with a spin (`cloud_bounces`; it can't eat a cloud), and after `chase_time` goes home. `ZurdMovementComponent` (wander, with a `far_speed` to head home fast; hunt with slowing near the target so it doesn't circle it; eat hold, hover, stun knock-back, retreat; between targets it keeps `ground_clearance` above the terrain, looks `look_ahead_time` ahead and climbs over ground, keeps out of other Zurds' bubbles (`bubble_scale` × body radius, pushing hard once they overlap) and out of the ship's `ship_space` (a soft push, off while it goes for food inside and while it eats); `process_fly_to` for the swoop and the chase; a moving home's velocity is carried; knocks around bodies it bumps) and `ZurdMouthComponent` (eats a target kept in the mouth for `eat_duration` divided by the eating speed; hands bites to the `MassManager` with `EventBus.eat_requested`, which takes one part of a combined object or the whole object and emits `object_eaten`).
- **GLB physics importer** (`scripts/import/glb_post_importer.gd`, `@tool EditorScenePostImport`; the project's default for scene imports via `[importer_defaults]` in `project.godot`, so new models need no import setup; a launchable one then needs a catalog entry, via *Sync with rigid scenes* on `data/object_catalog.tres`). It only touches models under `assets/models/`, and the folder opts each model into scenes: `objects/` → a `rigid/` `RigidBody3D` scene under `scenes/objects/` (one convex-hull collider, the exact hull of the mesh, at scale 1 and centred where the model's middle is + vertex colors), `scenery/` → a `static/` `StaticBody3D` scene (convex-hull colliders + vertex colors), any other folder (e.g. `characters/`, or `set_pieces/` for models wrapped by hand in `scenes/scenery/`) → no scenes. Every model gets its meshes as shared `.res` files under `assets/meshes/` and its vertex-color materials under `assets/materials/objects/`; a model left directly in `assets/models/` gets those plus a warning. The launcher and the sculpture-mass code depend on that collider layout (the catalog's check enforces it): `ObjectParts` reads an object's size from its first collision shape's scale and the launcher overwrites that scale, `MassPiece.get_center` averages shape positions, and growth break-off and the spin estimate measure each box or convex hull by its bounding box (`MassPiece.get_shape_bounds`); other shape types are left out of those measurements. Exact hulls cost more physics time than the old boxes (about 2.4× for 150 loose objects pressed together, 1.3× with fusing on; measured 2026-11-10). Changing the importer doesn't reimport existing models: select them in the FileSystem dock and press *Reimport* in the Import dock.
- **World** (`scenes/world/`; hardening plan step 2): `base_world.tscn` is the template every world builds on: `Environment` (`environment.tscn`: sky and light), `GameSystems` (`game_systems.tscn`: `MassManager`, `SculptureFx`, `CloudSky`, `ZurdDirector`), `Input` (`scenes/input/input.tscn`: `MouseSwatInput`; the lidar later) and `Actors` (`Ship` with `PlayerShip`, `Zurds`, `Objects`, `Masses`, `Projectiles`). A scene that builds on it and changes a value inside `GameSystems` marks it *Editable Children* (as `sandbox/test_sculpture_mass.tscn` does). `zurd_world01.tscn` is the main playable world (and the one the scene tests use): `base_world.tscn` plus `terrain.tscn` (`Terrain`, a `@tool` procedural landscape built in `_ready`, with a trimesh collider on layer 1 and a water plane at sea level; it also places the reflecting pool, position not final). **Reflecting pool** (`scenes/scenery/reflecting_pool.tscn`, the `reflecting_pool_01.glb` model with *Editable Children*): `ReflectingPool` (`@tool`) builds a purple outline along the basin's sharp and open edges (`edge_outline.gdshader`, lines a fixed number of pixels wide) and, in the game, a trimesh collider on layer 1 for the basin (the water isn't solid); both come from the mesh, so a re-export needs no changes. The basin uses `checkerboard.gdshader` (object-space squares, no UVs needed). `PlanarReflection` mirrors the active camera in the water plane and renders the scene into a texture for `reflecting_pool_water.gdshader` (mirror plus scrolling noise ripples), at `resolution_scale` of the screen and only while the water is on screen; without it (in the editor) the water shows its colour only. `zurd_world02.tscn` is the world in progress: `base_world.tscn` plus `terrain02.tscn` at Y 0, with the ship starting at Y 332.18. `terrain02.tscn` holds a solid 10 km `Floor` (a thin box collider on layer 1), two areas from `scenes/world/areas/` (`PoolCourt`: the reflecting pool, flute sections north/south/west/east and arches; `MegaTreeGrove`: the grove floor, the mega trees and the sky canopy), `BushGarden` and `CircleGrids`. **Solid scenery:** `SolidScenery` (`scenes/scenery/solid_scenery.gd`) on a scenery scene's root gives each mesh under it a trimesh collider on layer 1 in the game (shape kept on the mesh as meta, so copies share it; `exclude` keeps water non-solid); the flute sections, circle grids and bushes use it, the mega trees have an import-generated collider and the reflecting pool its own. **Mega trees and sky canopy** (`MegaTreeGrove`): `mega_tree.tscn` (group `mega_trees`) uses `sky_fade.gdshader`, which makes the trunk see-through between two heights measured above the trunk's foot along a slightly uneven line, so the trees vanish into the sky and moving them or the terrain keeps the look. `SkyCanopy` (`scenes/scenery/sky_canopy.tscn`, `@tool`; its height is the canopy's) builds stacked shells over every tree in `mega_trees`, as soft patches that merge where trees stand close (press *Refresh* after moving trees). They use `sky_canopy.gdshader`: domain-warped noise with time as an axis gives an organic outline that slowly changes, coloured from the sky behind it (`sky_match.gdshaderinc`) toward a faint gold, with an optional detail `canopy_texture`. Backdrop only. The world does **not** wrap (decided 2026-11-04; the toroidal world and `ToroidalUtils` were removed). Teleportation may come later for a small part of the map.
- **Sculpture masses** (`scenes/sculpture/`; spec in `claude/design/`, plan in `claude/plans/archive/`): `MassManager` (node in `game_systems.tscn`, holds all tunables) watches every body registered with `ObjectTracker`, counts hits, and does fusing, combining, merging, eating and breaking off. Contact callbacks only queue requests; the queue runs in the manager's `_physics_process`, because shapes can't change inside a physics callback. Each mass is one `SculptureMass` (`RigidBody3D`): fused objects become `MassPiece` nodes holding their visuals, while their `CollisionShape3D`s move onto the mass (meta `mass_piece` points back). Leaving a mass spawns a fresh instance of the object's scene. Matching objects (same model) that reach the hit count **combine** into one bigger object instead of fusing (Design Doc §4.10): every object carries an `ObjectParts` record (`scenes/sculpture/object_parts.gd`; meta `object_parts` on loose bodies, `MassPiece.parts` when fused) with each part's size and the size after each join; `combine_size_mode` adds volumes or scales. Counts, weights and cloud progress use parts, a growing piece knocks off the fused neighbours it now overlaps, and Zurds bite one part at a time (last added first). Before 100% fused objects use `assets/shaders/sculpture_mass.gdshader` (one material per mass; opaque so they stay solid and cast shadows, shifting only part of the way toward white). At 100% the mass swaps to its own copy of `sculpture_cloud.gdshader` with a white `burst` that settles over `cloud_transition_time`, `SculptureFx` puffs every object up (around its middle) and leaves it 1.2× bigger, so becoming a cloud is a jump, not a fade. The cloud look itself is a placeholder. The mass gathers its pieces under a `CloudBody` node at its middle before `cloud_formed` fires. **Cloud sky** (Cloud-Formation Design Doc §4; `CloudSky` in `game_systems.tscn` holds the tunables, the same in every world): a new cloud holds `rise_delay`, then over `rise_time` glides out and climbs along an arc to a random ring (`gyre_radius_range` around `gyre_center`, the world origin) and height (`zone_heights`, 1000–1550 m), growing to `scale_multiplier` (6×) its size. There every cloud circles the centre (`gyre_lap_time` at the middle ring, inner rings faster by `gyre_shear`), a gentle push moves overlapping clouds' orbits apart, and each bobs, tumbles slowly in any direction and breathes. `CloudSky.step` also runs on bare `SkyCloud` states (tests). The cloud look (`sculpture_cloud.gdshader`) is about 90% opaque and lit (white lit side, cool shadow), darkens gently toward the silhouette, and has darker, fully solid bottoms by world height (`SculptureMass.set_cloud_bounds`, called by `CloudSky` every frame). Each object mesh gets subtle ridge lines (`cloud_ridges.gdshader`, `cloud_ridges.tres`, render priority 2; lines on short on-screen edges fade). A model's ridges and puff surface table are worked out once (cached as meta on the mesh): its triangles are read on the main thread, one model per frame (several ms each, a GPU readback), the rest on a `WorkerThreadPool` task, so forming a cloud of new models doesn't stall the game; the ridges and puffs fill in during the white burst. `CloudPuffs` (a MultiMesh under each object mesh) scatters soft puffs over it; `CloudWisps` (under the mass at the body's middle, scaled with the cloud's growth) keeps 3–8 small puff clusters coming and going around it; both use `cloud_puff.gdshader` (`INSTANCE_CUSTOM` xyz seed, w fade) via `cloud_puff.tres` (render priority 1, after the clouds' objects). The ship camera's far plane is 12 km so the far side of the gyre stays visible. `SculptureFx` hooks placeholder effects to the EventBus signals. Test scene: `sandbox/test_sculpture_mass.tscn` (threshold 5, `hits_to_fuse` 1, debug labels).

## Workflow: plan before code, questions on review

- **No major code changes without a reviewed plan.** Before modifying any code, scene, shader or
  project setting, write a plan document in `claude/plans/` named `YYYY-MM-DD-<topic>-plan.md`
  (goal, files to touch, steps, risks, how it will be verified, open questions). Then stop and
  ask the user to review it. Start implementing only after the user explicitly approves the
  plan, and keep the changes inside the approved scope. If the work needs to grow beyond the
  plan, update the plan and get it approved again first.
  - Exempt: edits to docs/plans themselves, and trivial fixes the user asks for directly
    (typos, a one-line change they spelled out). When unsure, write the plan.
- **Start building from a clean tree.** Before implementing an approved plan (or a new step of
  one), run `git status`. If there are uncommitted changes, stop and ask the user whether to
  commit them first (the usual answer, so recommend it), keep them and build on top, or stop.
  This keeps each feature's changes separate from earlier work. Don't commit without the
  user's say-so.
- **Keep the tests passing; Claude maintains them.** Run the test suite (How to run) before
  committing code changes and report the result. When a change alters a tested rule on purpose,
  update the test in the same change. A plan for new behaviour lists the checks it adds to
  `tests/`, in place of a throwaway harness. Tests check rules, not tuning (`tests/README.md`).
- **Reviewing design docs and plans** (`claude/design/`, `claude/plans/`): when asked to review,
  or when writing a new one, ask as many clarifying questions as needed to fill gaps,
  ambiguities, contradictions with other docs or the code, missing edge cases and unstated
  tunables. Put them in **one numbered list** so the user can answer by number (`3: yes`), and
  group them under short headings if there are many. Don't fill gaps with silent assumptions:
  ask, or list the assumption as a question. After the answers come back, update the doc and
  ask follow-up questions (numbering continues) until nothing is open.

## Conventions Claude must follow

- **Commit messages** (from README): `tag(scope): description`. Tags: `feat`, `fix`, `docs`, `asset`, `tool`, `refactor`. Example: `feat(player): Added flight controls`.
- **File and folder names:** snake_case (the Godot standard; it avoids case problems in exported builds), except C# files, which must match their class.
- **GDScript and shader style:** indent with **tabs** (the GDScript style guide; every `.gd` and `.gdshader` file uses them and `.editorconfig` sets it); keep typed vars/returns and `class_name` as existing scripts do; use `push_warning`/`push_error` for diagnostics, not `print`.
- **C# style (lidar code only):** standard .NET — 4-space indent, file-scoped `namespace Zurd.Lidar;`, nullable enabled. A Godot node's class must be `partial` and its name must match its file name (`LidarSetup.cs` → `class LidarSetup`), so these files are PascalCase unlike the snake_case `.gd` files. Keep device logic in plain classes under `scripts/lidar/`; scenes only display it.
- **Vendored code (`thirdparty/`):** keep upstream's style so it can be compared with upstream. Mark every change with a `// zurd patch:` comment and list it in that folder's README.
- **Collision layers:** 1 Environment · 2 Player · 3 Objects · 4 Enemies · 5 UI (named in Project Settings → Layer Names, so the Inspector shows them).
- **Render layers:** 20 *No reflection*: the mirror camera of `PlanarReflection` leaves it out. Anything below a reflecting pool's water (its basin, the water itself) goes on it, since a camera can't clip at the water and would show it in the reflection.
- **Globals available everywhere:** `EventBus`, `SceneChanger`, `ObjectTracker`, `Controllers`.
- **Do not hand-edit generated files** — `scenes/objects/{static,rigid}/*`, `assets/meshes/*`, `assets/materials/objects/*`, `*.import`, `*.uid` (including `*.cs.uid`) come from the importer/engine; re-import the source `.glb` instead.
- **Do not** edit `.godot/` (gitignored) or commit `.vscode/`.

## Known gaps (documented, not yet fixed)

- **Lidar touches don't reach gameplay yet.** Only `MouseSwatInput` emits `EventBus.swat_requested` / `pointer_moved`. The bridge (`LidarManager`, step 4 of the lidar plan) waits until a lidar is set up against a screen or projection.
- **Zurds are at iteration 2.1** (see Enemy above): roles, individual anger and temperament, packs, feeding, growth and the cloud chase, but still two states, no killing, a placeholder look (role tints, red overlay, `Label3D` health and anger bars, testing HUD) and no sounds. Their numbers are starting points for playtesting. Objectives (which would ramp the difficulty) don't exist yet.
- **Model files aren't snake_case** (`Arch_01.glb`), and the importer copies those names into every generated scene, mesh and material. Rename them in the editor, renaming their generated files too (steps in `assets/models/README.md`).
- **Nothing despawns:** loose objects float forever and clouds never leave. There is no object budget, by choice (2026-11-12): the Zurds eating the mess should keep loose objects in check, and the number of clouds is for later. The world deliberately never resets between groups (decided 2026-11-11).
